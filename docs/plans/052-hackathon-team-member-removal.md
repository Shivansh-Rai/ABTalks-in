# 052 — Hackathon: remove a team member and fill the freed slot

## 1. Goal

Let a hackathon team leader remove a member from their team (with an admin
override for disputes), free that roster slot so anyone else can take it via the
existing team-code registration flow, and keep an append-only audit record of
every removal — including the case where the leader brings the *same* person
back into the team afterwards.

---

## 2. Current behavior

### Data model (`prisma/schema.prisma:844-875`)

- `HackathonTeam` — `entryType` (SOLO | TEAM), `teamName?`, `teamCode` (unique).
- `HackathonParticipant` — `userId` **unique** (one entry per person, FK →
  `User`, cascade), `slotIndex`, `isLeader`, denormalized identity fields
  (`fullName`, `email`, `phone`, `college`, `graduationYear`), `sourceSlug`
  (share-link attribution), `@@unique([teamId, slotIndex])`.
- `HACKATHON.maxTeamSize = 3` (`src/components/hackathon/hackathon-config.ts:5`).

### What exists

- Registration (`src/app/actions/hackathon-actions.ts`) supports `SOLO`,
  `TEAM_CREATE` (creator becomes `isLeader: true`, slot 1), and `TEAM_JOIN`
  (join by 6-char code, `isLeader: false`).
- `/hackathon/dashboard` renders `TeamRoster` (read-only list) plus `InvitePanel`
  (team code + copy button) when `spotsLeft > 0`.
- `/admin/hackathon` lists teams with expandable member rows, CSV export, and the
  problem-statement editor.

### What does not exist

- **No way to remove anyone.** There is no leader-facing or admin-facing control,
  and no server action. Today the only remedy is a manual DB edit.

### Blocking bug that must be fixed as part of this feature

`insertJoin` (`src/app/actions/hackathon-actions.ts:276-306`) computes:

```ts
const slotIndex = HACKATHON.maxTeamSize - spotsLeft + 1;   // === participantCount + 1
```

Remove the slot-2 member from a full 3-person team and the roster becomes
`{1, 3}` with `count = 2`. The next joiner computes `slotIndex = 3`, which
violates `@@unique([teamId, slotIndex])`. The existing race handler re-fetches
and recomputes **the same 3**, fails again, and the replacement member sees
*"That team just filled up. Ask your leader for another team."* — i.e. the
replacement can never join. Slot allocation must become "lowest free slot in
`1..maxTeamSize`".

A second, smaller defect in the same function: it treats **any** P2002 as a slot
race, so a double-submit (P2002 on `userId`) also reports "team just filled up".

### Decisions taken (confirmed with the owner, 2026-07-31)

| Question | Decision |
| --- | --- |
| Who can remove | **Leader + admin.** Leader from `/hackathon/dashboard`; admin from `/admin/hackathon` as an override. |
| How the replacement is added | **Existing team-code registration.** Removal frees a slot → `spotsLeft` rises → `InvitePanel` reappears → the new person registers at `/hackathon/register` with the same code. No invite-by-email, no schema change to `userId`. |
| Timing lock | **Leader removals allowed through Tue 4 Aug IST**, then locked — a new `HACKATHON.rosterLockUtc` deadline, 3 days before kickoff. **Admin has no time limit.** |
| Audit trail | **New `HackathonRemoval` table.** The participant row is *hard-deleted* (frees `userId @unique` so re-registration just works, and frees the slot); the log preserves the snapshot. |

Rejected: soft-delete via `removedAt` on `HackathonParticipant`. It would block
re-registration (`userId @unique` still held; a Postgres partial unique index is
not cleanly expressible in Prisma) and would require a `removedAt: null` filter
in ~10 existing read paths (`getMyRegistration`, `isUserRegistered`,
`getTeamByCode._count`, `getTeamLeader`, `getAdminData`,
`getHackathonMasterStudents`, `getHackathonLinkStats`,
`get-analytics-data.ts:106`, `get-registration-dates.ts`) where a single miss
silently corrupts registration counts.

## 5. Steps

### Step 1 — Schema: add the removal log

In `prisma/schema.prisma`, next to the other hackathon models (after
`HackathonParticipant`, before `HackathonEvent`):

```prisma
enum HackathonRemovalActor {
  LEADER
  ADMIN
}

/// Append-only log of hackathon team removals. The `HackathonParticipant` row is
/// hard-deleted on removal — that frees `userId @unique` (so the person can
/// register again, including back into the same team) and frees the slot. This
/// table preserves who was removed, by whom, and their original share-link
/// attribution so a rejoin keeps its `sourceSlug`.
model HackathonRemoval {
  id               String                @id @default(cuid())
  teamId           String
  teamCode         String
  teamName         String?
  userId           String
  fullName         String
  email            String
  phone            String
  college          String
  graduationYear   Int
  slotIndex        Int
  sourceSlug       String?
  originalJoinedAt DateTime
  removedByUserId  String
  removedByRole    HackathonRemovalActor
  reason           String?
  createdAt        DateTime              @default(now())

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId, createdAt(sort: Desc)])
  @@index([teamId])
  @@index([createdAt(sort: Desc)])
}
```

Add to the `User` model relation block (near `hackathonParticipant`, around
`prisma/schema.prisma:283`):

```prisma
  hackathonRemovals                  HackathonRemoval[]
```

Deliberate choices — **do not "improve" these**:

- `teamId`, `teamCode`, `teamName` are **plain columns with no FK**. A FK with
  cascade would delete audit history when a team is deleted, defeating the point.
- `removedByUserId` is a **plain column with no FK**, for the same reason.
- `userId` **does** cascade from `User`. This is required: `prisma/cleanup.ts`
  deletes users and relies on cascades — without it, `db:cleanup` fails on an FK
  violation.

Then run the migration (see §7 for the safety sequence first):

```bash
npx prisma migrate dev --name hackathon_member_removals
```

### Step 2 — Config: the roster-lock deadline, and validation schema

**2a. `src/components/hackathon/hackathon-config.ts`** — add exactly two keys,
directly under the existing date block (after `registrationClosesLabel`):

```ts
  // Leaders can edit the roster (remove a teammate) up to and including
  // Tue 4 Aug IST — 3 days before kickoff. This instant is 5 Aug 00:00 IST, so
  // the whole of 4 Aug is still open. Admins are never subject to this lock.
  rosterLockUtc: "2026-08-04T18:30:00Z", // Tue 4 Aug 11:59 PM IST (= 5 Aug 00:00 IST)
  rosterLockLabel: "Tuesday, 4 Aug · 11:59 PM IST",
```

Notes:

- This is a **separate deadline from `kickoffUtc`** and deliberately earlier.
  Do not derive it from `kickoffUtc` with arithmetic (`kickoff - 3 days`) — the
  organizer moves these dates by hand and a derived value would silently drift.
- `18:30:00Z` is 00:00 IST on 5 Aug, i.e. the end of 4 Aug IST. The comparison
  is `Date.now() >= rosterLockUtc`, so 4 Aug 11:59 PM IST is still allowed and
  5 Aug 00:00 IST onwards is locked — matching "until 4 August".
- `kickoffUtc`, `deadlineUtc`, and every other key in this file stay exactly as
  they are. The three `TODO(organizer)` date values are **not** yours to change.

### Step 3 — `src/features/hackathon/remove-participant.ts` [new]

`import "server-only";` at the top. Two exports.

**`removeParticipant(args)`** — the single transactional removal path used by
both actions:

```ts
export type RemoveParticipantResult =
  | {
      ok: true;
      data: {
        userId: string;
        fullName: string;
        email: string;
        slotIndex: number;
        teamId: string;
        teamCode: string;
        teamName: string | null;
        spotsLeft: number;
      };
    }
  | { ok: false; message: string };

export async function removeParticipant(args: {
  participantId: string;
  teamId: string; // authorization scope — must match the participant's own teamId
  removedByUserId: string;
  removedByRole: "LEADER" | "ADMIN";
  reason?: string | null;
}): Promise<RemoveParticipantResult>
```

Body — everything inside one `prisma.$transaction(async (tx) => { ... })`:

1. `const target = await tx.hackathonParticipant.findFirst({ where: { id: args.participantId, teamId: args.teamId }, select: { ... } })`
   selecting `id, userId, slotIndex, isLeader, fullName, email, phone, college,
   graduationYear, sourceSlug, createdAt` plus
   `team: { select: { id: true, teamCode: true, teamName: true, entryType: true } }`.

   **Scoping by both `id` AND `teamId` in one query is the authorization check** —
   it makes a forged `participantId` from another team simply not found. Do not
   look the participant up by `id` alone and compare afterwards.

2. `if (!target) return { ok: false, message: "That member is no longer on this team." }`
3. `if (target.isLeader) return { ok: false, message: "The team leader can't be removed." }`
4. `if (target.team.entryType === "SOLO") return { ok: false, message: "Solo entries have no team members to remove." }`
   (defensive — unreachable once 3 passes, since a SOLO team's only participant
   is the leader).
5. `await tx.hackathonRemoval.create({ data: { ... } })` — snapshot every identity
   field from `target`, `teamId: target.team.id`, `teamCode: target.team.teamCode`,
   `teamName: target.team.teamName`, `originalJoinedAt: target.createdAt`,
   `removedByUserId`, `removedByRole`, `reason: args.reason ?? null`.
6. `await tx.hackathonParticipant.delete({ where: { id: target.id } })`
7. When `args.removedByRole === "ADMIN"`, also
   `await tx.adminAction.create({ data: { adminUserId: args.removedByUserId, targetUserId: target.userId, actionType: "REMOVE_HACKATHON_TEAM_MEMBER", metadata: { teamCode, teamName, slotIndex, participantId }, reason: args.reason ?? null } })`
   — matches the existing convention in `admin-hackathon-actions.ts:32`.
8. `const remaining = await tx.hackathonParticipant.count({ where: { teamId: args.teamId } })`
   → return `spotsLeft: HACKATHON.maxTeamSize - remaining` (used in the leader
   email).

Wrap the whole transaction in `try/catch`; on error `logger.error("hackathon
participant removal failed", { error })` and return
`{ ok: false, message: "Something went wrong. Please try again." }`. Never throw
out of this function.

### Step 6 — Fix slot allocation in `src/app/actions/hackathon-actions.ts`

This is the **load-bearing fix**; without it, no replacement can ever join a team
that had a removal.

Replace the whole `insertJoin` function (currently lines 276-306) **and** its
three call sites (the `first` / `refreshed` / `second` sequence, lines 308-367)
with a single retry loop.

New `insertJoin` — takes only `teamId`, allocates the lowest free slot inside the
transaction:

```ts
type JoinFailure = "full" | "already-registered" | "slot-race" | "error";
type JoinResult = { ok: true } | { ok: false; kind: JoinFailure };

async function insertJoin(teamId: string): Promise<JoinResult> {
  try {
    return await prisma.$transaction(async (tx) => {
      const taken = await tx.hackathonParticipant.findMany({
        where: { teamId },
        select: { slotIndex: true },
      });
      const used = new Set(taken.map((r) => r.slotIndex));
      let slotIndex = 0;
      for (let i = 1; i <= HACKATHON.maxTeamSize; i++) {
        if (!used.has(i)) {
          slotIndex = i;
          break;
        }
      }
      if (slotIndex === 0) return { ok: false as const, kind: "full" as const };

      // A previously-removed member rejoining THIS team keeps their original
      // share-link attribution, so a remove/re-add cycle can't re-attribute the
      // signup to a different link. Fresh joiners use the current visit cookie.
      const priorRemoval = await tx.hackathonRemoval.findFirst({
        where: { userId, teamId },
        orderBy: { createdAt: "desc" },
        select: { sourceSlug: true },
      });

      await tx.hackathonParticipant.create({
        data: {
          teamId,
          userId,
          slotIndex,
          isLeader: false,
          fullName: d.fullName,
          email: d.email,
          phone: d.phone,
          college: d.college,
          graduationYear: d.graduationYear,
          sourceSlug: priorRemoval ? priorRemoval.sourceSlug : sourceSlug,
        },
      });
      return { ok: true as const };
    });
  } catch (error) {
    if (isPrismaUniqueViolation(error)) {
      const e = error as Prisma.PrismaClientKnownRequestError;
      if (uniqueTargetIncludes(e, "userId")) {
        return { ok: false, kind: "already-registered" };
      }
      if (uniqueTargetIncludes(e, "slotIndex")) {
        return { ok: false, kind: "slot-race" };
      }
    }
    logger.error("hackathon join participant insert failed", { error });
    return { ok: false, kind: "error" };
  }
}
```

Call site — replace lines 308-367 with:

```ts
let joined: JoinResult = { ok: false, kind: "slot-race" };
for (let attempt = 0; attempt < HACKATHON.maxTeamSize; attempt++) {
  joined = await insertJoin(team.id);
  if (joined.ok || joined.kind !== "slot-race") break;
}

if (!joined.ok) {

  }

      message: "Something went wrong. Please try again.",
    };
  }
  return {
    ok: false as const,
    message: "That team just filled up. Ask your leader for another team.",
  };
}

await sendTeamJoinEmails({
  teamId: team.id,
  teamName: team.teamName,
  memberName: d.fullName,
  memberEmail: d.email,
  teamCode: d.teamCode,
});
(await cookies()).delete(SRC_COOKIE_NAME);
return {

    entryType: "TEAM_JOIN" as const,

```

Notes:

- Only `"slot-race"` retries. `"full"` and `"already-registered"` are terminal.
- The pre-flight `team.spotsLeft <= 0` check above (line 272) stays as-is — it's
  a fast path; `insertJoin`'s `"full"` result is the authoritative one.
- The `SOLO` / `TEAM_CREATE` branch above is **unchanged** — it hardcodes
  `slotIndex: 1` on a brand-new team, which is always correct. A rejoining
  removed member who creates their *own* team gets fresh cookie attribution;
  that is intentional.
- `sendTeamJoinEmails` already fires for TEAM_JOIN, so a returning member gets
  the member-welcome email again and the leader gets the new-member email. **No
  change needed there** — do not add a special "welcome back" variant.
