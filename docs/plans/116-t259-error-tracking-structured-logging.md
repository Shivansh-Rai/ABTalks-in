## 1. Outcome (verbatim, from workbook)

> As the team, we hear about production errors before users report them.

## 2. Definition of Done (verbatim)

> Production error tracking is live and reporting. Structured logs carry useful identifiers for the money and contact paths. Email and notification failures are logged with a reason.

## 3. Regression guard (verbatim)

> Never log a password, a token or protected contact details.

## 4. Acceptance test

> Force an error in a non-critical path and confirm it reaches the tracker with a useful identifier. Force an email failure and confirm the reason is logged.

## 5. What to build

Three deliverables:

### 5.1 Production error tracker

- Choose Sentry (industry standard for Next.js; explicit deliverable of T-259 so this is not the same "team-infra decision" question as Playwright — the workbook requires it).
- Install `@sentry/nextjs`, run the wizard, gate init on `isProduction()` from `src/lib/env.ts` (already built in T-252 — reuse it).
- Set `SENTRY_DSN` in Vercel Production env only.
- Add `beforeSend` and `beforeBreadcrumb` scrubbers so passwords, tokens, emails and phone numbers are redacted even if they slip into an error message.

### 5.2 Structured logger

- Install `pino` + `pino-pretty` (dev formatter).
- Central logger in `src/lib/log/logger.ts` with a `redact` config listing every PII path — passwords, tokens, authorization headers, emails, phones, contact, resume text, notes, assessment answers.
- Export named helpers for the two paths the workbook calls out:
  - `logMoney(op, ctx)` — recruiter_id, candidate_id, amount_cents, ledger_id, idempotency_key, outcome, reason
  - `logContact(op, ctx)` — recruiter_id, candidate_id, unlock_id, outcome, reason
- Both helpers accept only opaque IDs and enums. Never accept raw email/phone/contact. Redact belt-and-braces catches accidents.

### 5.3 Notification-failure logging shape

- Publish the log shape T-268 (16 Sep) will read from. Do it as a helper `logNotificationDelivery(ctx)` that takes: event, recipient_id, channel, attempt, outcome (ok/failed), provider, provider_status, reason.
- T-248 (tomorrow, also Manuvrtti) plugs into this helper from the notification service. Getting the shape right today means T-248 lands cleanly tomorrow and T-268 falls out easily on 16 Sep.

## 6. Non-negotiable constraints

- **No passwords, tokens, or protected contact details in any log line, ever.** Redact rules catch accidents but do not depend on them — write defensively.
- **No exception messages that embed user data.** `throw new Error(\`no user with email ${email}\`)` is banned. Use `throw new Error('no user found', { cause: { user_id }})` — the ID is safe, the email is not.
- **Init gated on `isProduction()`.** Sentry must not send from dev or preview.
- **Do not modify middleware.ts.** Same rule as T-252 — Edge runtime forbids `@/lib/*` imports.

## 8. Tests

Same tsx pattern as `consent.test.ts` (established in T-252, no new test infra).

**Redaction contract:**
- Pass a payload containing `{ password: 'x', email: 'a@b.com', phone: '+91...', token: 'abc', normal_field: 'ok' }` → the resulting log entry contains `[redacted]` for the sensitive fields, keeps `normal_field`.
- Test that nested paths (`{ user: { email: '...' } }`) are also redacted.

**Helper shape contract:**
- `logMoney({ recruiter_id, candidate_id, amount_cents, outcome: 'ok' })` writes a line with area='money', op set, and the ctx fields present.
- `logNotificationDelivery` writes with area='notification', all delivery fields present.

**Sentry init gating:**
- With `isProduction()` mocked to `false`, `Sentry.init` is called with `enabled: false` (or not called at all — whichever matches Sentry v9's API).

## 12. Decision record (written during implementation, 2026-09-09)

Six places where the build departed from §5–§8. Each is a deliberate call, not
an oversight; overrule any of them and the change is small.

### D-1 — The logger lives at `src/lib/logger.ts`, not `src/lib/log/logger.ts`

§7 lists `src/lib/log/logger.ts` as `[new]`. A central logger already existed at
`src/lib/logger.ts` — a `console.*` shim with **111 importers**. Creating the
planned path would have meant either two loggers, or a 111-file rename for no
behavioural gain. The existing module was rewritten onto `pino` instead, keeping
its `logger.info(message, meta)` signature so no call site moved, and adding
pino's own `logger.info(meta, message)` order for new code. Both produce the
same JSON.

### D-2 — `middleware.ts` WAS modified, and the constraint behind §6 still holds

§6 says "Do not modify middleware.ts", giving the reason: the Edge runtime
forbids `@/lib/*` imports. But §Part 4 of the task requires a request id that
reaches application logs, and middleware is the only place every request passes
through. The stated *reason* was preserved rather than the letter:

- **no `@/lib/*` import was added.** The header name and validation pattern are
  duplicated by hand, exactly as the consent-cookie constants above them already
  are, with a comment pointing at `src/lib/observability/request-id.ts`.
- **measured, not assumed.** After the change the middleware bundle is
  **326,622 bytes (0.311 MB)** against the 1 MB limit, and 304 KB of that is the
  pre-existing next-auth/jose chunk. No Sentry or pino code is in it.
- **the existing behaviour is under test.** `request-id.test.ts` drives the real
  middleware and asserts the auth redirect, the referral cookie and the consent
  gate all still behave, on every branch.

If the constraint is meant literally, the alternative is a request id generated
per Server Action instead of per request — cheaper to revert, but it stops
correlating a page render with the actions fired from it.

### D-3 — camelCase context fields, not snake_case

§5.2/§5.3 wrote `recruiter_id`, `amount_cents`, `provider_status`. The helpers
use `recruiterId`, `amount`, `providerStatus`. Every other structured field in
this codebase is camelCase (`userId`, `deliveryId`, `idempotencyKey`), and a log
line split between two conventions is worse for a consumer than either. The
*set* of fields is the plan's. `amount_cents` became `amount` because this
product's money is Synergy Points, not currency — "cents" would be a lie in the
field name.

### D-4 — No `sentry.edge.config.ts`

§7 lists one. Initialising Sentry in the Edge runtime pulls the SDK into the
bundle that CLAUDE.md caps at 1 MB — the same constraint §6 is protecting. The
app declares no `runtime = "edge"` route, so every server error already lands in
the Node runtime and is captured there. If an Edge route is added later, this is
the decision to revisit.

### D-5 — Instrumentation went further than §11 scoped

§11 puts "wiring `logMoney`/`logContact` into call sites" out of scope, leaving
it to T-228/229/230/232 and T-248. The task as commissioned required the real
paths instrumented, so they were: `applyPointsChange` (every credit and debit),
`insertLedger`, `redeemItem`, `hasContactAccess` / `contactAccessFor`, the
engagement request and admin `CONTACT_SHARED` decision, the hire-alert outreach,
and the contact form. This does not conflict with those tasks — the helpers are
published exactly as §5.2 specifies, and the wiring is an example of their use.

### D-6 — Verification is an automated test, not a `/api/dev/boom` route

§9/§10 propose a hidden route that throws, plus a dashboard screenshot.
`sentry-delivery.test.ts` stands up a throwaway HTTP endpoint, points a DSN at
it, and asserts on the bytes the real SDK puts on the wire: the event id, the
`requestId`/`deliveryId` tags, and the *absence* of the password, token, cookie,
email and phone deliberately planted in the error, the scope and the
breadcrumbs. That is stronger evidence than a screenshot, it runs on every
change, and it leaves no unauthenticated error endpoint in production.

**It found two real defects that a screenshot would not have.** First, Sentry's
`ContextLines` integration attaches the *source code* around the throwing line,
so any literal near a throw ships with the error; it is now disabled in both
configs and stripped in `beforeSend`. Second, `await import("@sentry/nextjs")`
under a CommonJS loader hoists `init` but leaves `captureException` on
`.default`, which made reporting a silent no-op in exactly the environments
least likely to be watched.

### Deployment checklist (nothing below can be done locally)

1. Create the Sentry project (platform: Next.js). Nothing reports until this
   exists — there is no `SENTRY_*` variable in `.env` or `.env.local` today.
2. Vercel → Settings → Environment Variables, **Production scope only**:
   - `SENTRY_DSN` — server DSN
   - `NEXT_PUBLIC_SENTRY_DSN` — same DSN; ships to the browser, which is safe
     (a DSN only permits writing events)
   - optional, for readable stack traces: `SENTRY_AUTH_TOKEN`, `SENTRY_ORG`,
     `SENTRY_PROJECT`
3. Confirm `NEXT_PUBLIC_APP_ENV=production` is set on Production and **not** on
   Preview — that variable alone is what separates the two.
4. Deploy with `npm run build:deploy` so `prisma migrate deploy` applies
   `20260909180000_t259_notification_delivery` before the new code runs. The
   delivery write is best-effort, so deploying without it degrades to a warning
   rather than breaking mail — but the row is what T-268 reads.
5. Smoke test: force a send failure (temporarily bad `BREVO_API_KEY` on a
   preview) and confirm one `NotificationDelivery` row, one `notification.failed`
   log line and one Sentry issue, all carrying the same `deliveryId`.

## 15. Live verification (2026-09-09, against `abtalks-production`)

Raw envelope POST returned **HTTP 200** with server-assigned id
`b549acb6f88d46618656dedad44d46a1`, confirming the DSN is accepted — the SDK
mints an event id locally whether or not ingest accepts it, so `flush()`
returning true proves nothing on its own. This is how the first run, made with a
truncated key, looked successful while landing nothing.

That run also found a genuine leak: `"password":"not-a-real-password"` inside a
provider error message survived, while the planted email, API key and phone were
all redacted. A password has no recognisable shape — only a key beside it — and
providers echo request bodies into error messages. Fixed with JSON and
`key=value` matching in `scrubString`, covered by two regression tests: one that
the secrets die, one that ordinary log lines (`event=`, `score=`, ids) survive
untouched, because over-redaction is its own failure.
